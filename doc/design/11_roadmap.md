# 11 · 开发路线图

> 本文档定义《Agamemnon》从单机 Demo 到正式上线的完整开发规划。

---

## 一、总路线概览

```
Phase 0: 单机 Demo         (4~6 周)   ← 当前阶段
    ↓
Phase 1: C++ 核心重构       (3~4 周)
    ↓
Phase 2: 联网对战系统       (6~8 周)
    ↓
Phase 3: 内容扩充           (4~6 周)
    ↓
Phase 4: Steam EA 上线      (2 周)
    ↓
Phase 5: 正式 1.0 版本      (持续运营)
```

**预计首发时间**：自 Phase 0 起算 **约 7~9 个月** 达到 EA

---

## 二、Phase 0 · 单机 Demo（⭐ 当前阶段）

### 2.1 目标

> 用最简方式验证核心玩法，让 1 人 + 3 AI 能完整打完一局游戏。

### 2.2 功能清单

| 模块 | 优先级 | 说明 |
|------|--------|------|
| **主菜单** | P0 | "开始游戏" + "退出" 两个按钮 |
| **英雄选择** | P0 | 3 个英雄，显示被动/主动 |
| **仓库生成** | P0 | 10×200 网格 + 紧密填充 + 20 个物品模板 |
| **揭露系统** | P0 | L0~L4 五层级，持久化 |
| **出价系统** | P0 | 密封输入、回合倍率判定 |
| **AI 玩家** | P0 | 3 档 AI，能正常出价决策 |
| **回合状态机** | P0 | 10 回合流程 |
| **结算系统** | P0 | 评分计算、UI 显示 |
| **排位分显示** | P1 | 本地显示（不存档） |
| **简单 UI** | P1 | 能用即可，不求精美 |
| **主动技能** | P1 | 至少 1 个英雄的主动能用 |

### 2.3 Demo 里**不做**的事

- ❌ 联网 / 多人
- ❌ C++ / GDExtension（全用 GDScript）
- ❌ Steam 接入
- ❌ 天赋系统
- ❌ 多种仓库类型
- ❌ 美术资源（用色块+图标）
- ❌ 音效音乐
- ❌ 存档 / 账号 / 段位持久化

### 2.4 详细开发节奏

| 周 | 任务 |
|---|------|
| **Week 1** | 项目结构搭建 + 仓库生成算法 + 物品数据模型 |
| **Week 2** | 揭露系统 + 仓库面板 UI（可滚动） |
| **Week 3** | 回合状态机 + 出价系统 + 判定逻辑 |
| **Week 4** | AI 决策（3 档） + 主动技能 |
| **Week 5** | 结算系统 + 评分 + UI 完善 |
| **Week 6** | Bug 修复 + 内测 + 反馈迭代 |

### 2.5 Demo 验收标准

- ✅ 从主菜单点到游戏结束，全程不闪退
- ✅ 4 人（1玩家 + 3 AI）能在 12 分钟内玩完一局
- ✅ 不同 AI 表现出明显差异（简单 AI 比困难 AI 好赢）
- ✅ 至少 10 位内部玩家测试，平均好评 3/5 星以上
- ✅ 玩家能在不看说明的情况下，15 分钟内学会玩法

## 三、Phase 1 · C++ 核心重构（3~4 周）

### 3.1 目标

> 把性能敏感/未来要联网的核心逻辑迁移到 C++（GDExtension），UI 层保持 GDScript。

### 3.2 迁移范围

| 模块 | 迁移到 C++ | 原因 |
|------|-----------|------|
| 仓库生成 | ✅ | 生成算法需要速度 |
| 揭露系统数据层 | ✅ | 未来要服务端权威 |
| 估值/结算逻辑 | ✅ | 未来要服务端权威 |
| AI 决策 | ✅ | 性能 + 未来可跑多个 AI |
| 状态机 | ✅ | 未来服务端要复用 |
| UI 交互 | ❌ | 保持 GDScript（灵活性） |
| 动画/特效 | ❌ | 保持 GDScript |

### 3.3 开发节奏

| 周 | 任务 |
|---|------|
| **Week 1** | 完成 CMakeLists + register_types + 能编译 |
| **Week 2** | 迁移仓库生成 + 揭露系统 + 数据模型 |
| **Week 3** | 迁移 AI 决策 + 状态机 |
| **Week 4** | 联调 + 性能测试 + 回归验证 |

### 3.4 技术要点

- 使用 godot-cpp 绑定
- C++ 层暴露 `Ref<T>` 对象给 GDScript
- 避免 C++ ↔ GDScript 频繁跨语言调用（批量操作）
- 单元测试框架（如 Catch2）用于 C++ 核心

### 3.5 验收标准

- ✅ Demo 所有功能依然正常工作
- ✅ 仓库生成速度 > 10 仓库/秒
- ✅ 100 局 AI vs AI 稳定不崩溃
- ✅ 内存无泄漏

## 四、Phase 2 · 联网对战系统（6~8 周）

### 4.1 目标

> 4 人真实联机，独立服务器权威仲裁。

### 4.2 架构

```
┌──────────────────┐
│ 匹配服务器        │
│ (Matchmaker)     │
└────────┬─────────┘
         ↓ 分配房间
┌──────────────────┐
│ 拍卖房服务器      │
│ (Auction Server) │ ← 权威，跑在云上
└────────┬─────────┘
         ↕ ENet / WebSocket
┌──────────────────┐
│ 客户端 (Godot)    │
└──────────────────┘
```

### 4.3 核心任务

| 任务 | 难度 |
|------|------|
| 独立服务器开发（C++） | ⭐⭐⭐⭐ |
| 网络协议设计 | ⭐⭐⭐ |
| 客户端网络层 | ⭐⭐⭐ |
| 匹配系统 | ⭐⭐⭐⭐ |
| 防作弊（服务器验证） | ⭐⭐⭐⭐ |
| 断线重连 | ⭐⭐⭐⭐⭐ |
| 服务器部署 / 运维 | ⭐⭐⭐ |
| 数据库 / 持久化 | ⭐⭐⭐ |

### 4.4 开发节奏

| 周 | 任务 |
|---|------|
| **Week 1** | 网络协议设计 + 服务器脚手架 |
| **Week 2** | 状态同步 + 房间管理 |
| **Week 3** | 客户端网络层 + 断线重连 |
| **Week 4** | 匹配系统 + 数据库 |
| **Week 5** | 压测 + 性能优化 |
| **Week 6** | 防作弊 + 安全加固 |
| **Week 7~8** | 云部署 + 内测 |

### 4.5 验收标准

- ✅ 100 人同时在线无问题
- ✅ 4 人联机完整一局稳定
- ✅ 延迟 < 200ms（国内节点）
- ✅ 断线重连成功率 > 95%
- ✅ 无明显作弊漏洞（经内部安全测试）

## 九、风险识别

### 9.1 技术风险

| 风险 | 影响 | 对策 |
|------|------|------|
| GDExtension 调试困难 | Phase 1 延期 | 前期建设完善日志/调试工具 |
| 服务器性能不足 | Phase 2 返工 | 压测前置，早发现问题 |
| 反作弊被破解 | 游戏公平受损 | 多层防御，服务端权威 |

### 9.2 玩法风险

| 风险 | 影响 | 对策 |
|------|------|------|
| 玩家觉得"估值"太累 | 留存低 | 加入估值辅助 UI |
| 平衡性难调 | 某英雄碾压 | 数据驱动迭代，AB 测试 |
| 学习门槛高 | 新手流失 | 新手引导 + 人机练习 |

### 9.3 市场风险

| 风险 | 影响 | 对策 |
|------|------|------|
| 同类竞品抢先 | 市场压力 | 先推 Demo 抢占心智 |
| 玩法太小众 | 销量低 | 提前做玩家调研 |
| 中国版号问题 | 国内无法上线 | 先做海外 Steam，再看版号 |
